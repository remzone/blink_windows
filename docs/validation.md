# Проверка Windows 0.1.0

Работы выполняются на Linux, 17 ноября 2026. Ниже отдельно перечислены доступные локальные проверки и действия, которые требуют Windows. Проверка ядра не равна проверке готового VPN-клиента.

## Автоматические проверки

- Сверка 89 файлов native-снимка с Android-источником с нормализацией module prefix: `python3 tools/check-native.py /path/to/blink-android/native`.
- Общий пакетный core, парсеры и VK TURN: `go test -race ./native/...`. Сетевые тесты используют локальные синтетические peers, а не реальные подписки и VK-реквизиты. Внешние live-проверки, требующие переменных окружения, не включались.
- Windows-слой импорта: `go test -race ./internal/client`. Обычные plain/base64 fixtures, сохранение четырёх официальных доменов VK, native handoff, истечение срока, дата из будущего, откат revision, дубликаты JSON, некорректные URL, неподдерживаемая маршрутизация и ограничение вложенности JSON.
- Windows EXE: кросс-компиляция `GOOS=windows GOARCH=amd64 CGO_ENABLED=0` с UAC-манифестом, `go vet` Windows-пакетов, компиляция Windows-теста DPAPI.
- ZIP: официальный Wintun 0.14.1 проверяется по закреплённому SHA-256; в пакет включаются DLL, лицензия, EXE и документация. SHA-256 итогового ZIP находится в `dist/SHA256SUMS`.
- Python-скрипты проверяются `python3 -m py_compile tools/package.py tools/check-native.py`.

Windows-тест DPAPI проверяет шифрование, чтение, атомарную перезапись и отказ при подмене ciphertext. На Linux он только компилируется. Ручной workflow `Validate Windows client` запускает тесты на Windows и собирает ZIP; его наличие не означает, что workflow уже запускался.

## Локальный результат

Пройдены: native-снимок 89 файлов, `go test -race ./native/...`, `go test -race ./internal/client`, Windows `go vet`, кросс-компиляция EXE и Windows DPAPI test executable, Python syntax check и упаковка с проверенным Wintun. Windows DPAPI test executable **не запускался**. Workflow GitHub Actions, реальный Windows GUI/драйвер/маршруты, live VK и серверы провайдеров **не проверялись**.

## Перед первым повседневным использованием — на Windows

1. Проверить UAC, старт окна, Tab/Shift+Tab, список, импорт из файла и вставки, читаемость при масштабах 100/150/200% и на нескольких мониторах.
2. Импортировать синтетические профили. Ошибка импорта должна оставить прежний список и зашифрованное состояние. После перезапуска профили доступны той же учётной записи; другая учётная запись не должна расшифровать их.
3. Подключить известный рабочий IPv4 VLESS/REALITY сервер. Проверить адрес/MTU Wintun, две `/1`, NRPT и временное IPv6-правило. Сверить внешний IP через кнопку и браузер.
4. Повторить для обычного WG, AWG, TUIC, Hysteria, Xray JSON/XDRIVE и частичных AllowedIPs на соответствующих известных серверах. Ни импорт, ни сборка не удостоверяют доступность всех протоколов.
5. Выполнить DNS/IPv6 leak checks и проверить доступ к локальной сети, DoH браузера, корпоративную NRPT/GPO, параллельные VPN и firewall. При конфликте политик подключение должно завершиться с ошибкой и очисткой.
6. Проверить VK с реальной действующей scoped-подпиской. Зафиксировать этапы без копирования реквизитов: TURN/DTLS/smux ready, затем успешный HTTPS. Если нужна современная CAPTCHA, ожидаемое поведение 0.1.0 — уведомление об отсутствии SDK и возможность отменить; это известное ограничение.
7. Отключить и закрыть окно. Проверить отсутствие маршрутов Blink, DNS-правила `Blink.Windows temporary` и firewall `Blink-IPv6`.
8. Принудительно завершить процесс в тестовом окружении, затем `Blink.exe --recover`. Убедиться, что собственные правила удалены, исходные маршруты и настройки физического интерфейса сохранены.
9. Проверить сон/пробуждение, смену Wi-Fi/Ethernet, потерю сервера и истечение Vokop-подписки. После смены физической сети требуется переподключение.
10. Проверить второй запуск клиента: он не должен менять адаптер активного экземпляра.

Установщика, Authenticode-подписи EXE, тестирования на физической Windows и аудита отсутствия сетевых утечек пока нет. Полноценная современная CAPTCHA и routing Vokop v3 остаются отдельными задачами.
