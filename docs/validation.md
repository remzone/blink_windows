# Проверка Windows 0.3.0-preview.4

## Подтверждение работы на Windows — 18 ноября 2026

Пользователь подтвердил: «на винде все работает» после установки 0.3.0-preview.4 с динамической WFP-защитой. Предшествующие журналы в этой сессии относятся к Windows build 26200 и процессу amd64. Это подтверждение работы приложения и подключения в пользовательском окружении; отдельные результаты по каждому протоколу, Windows 10 x86, DNS/IPv6-утечкам и аварийному удалению фильтров не предоставлены.

Ранее отмеченное отсутствие проверки реального подключения для preview.4 больше не актуально. Локальные проверки и Windows CI перечислены отдельно ниже; пользовательское подтверждение не означает успешного запуска CI.


Работа выполняется на Linux. Сборка, тестирование frontend и реальный Windows runtime — разные уровни проверки.

## Выполнено локально

- Общий core и Windows-импортёр: `go test -race ./internal/... ./native/...` — успешно. Native tests используют синтетические локальные peers; live-провайдеры не включались.
- `go vet` Windows-пакетов для amd64 и 386 — успешно.
- Кросс-компиляция EXE для обеих архитектур: x64 PE32+ AMD64 и x86 PE32 Intel 80386. Это отдельные сборки с подходящими resource objects, не переименованные файлы.
- Windows-тесты DPAPI, сетевой валидации, прямого чтения route table и изоляции PowerShell stderr скомпилированы отдельно для amd64/386. На Linux они не запускаются.
- 89 native-файлов совпадают с Android-снимком после нормализации module prefix.
- Официальный Wintun ZIP проверен по закреплённому SHA-256. Packager выбирает AMD64/x86 DLL соответственно и создаёт два ZIP с лицензиями и SHA256SUMS.
- Переносимые regression tests выбора интерфейса: метрика route+interface, исключение Blink/offline/нулевого индекса, отсутствие default route, детерминированные равные метрики и защита суммы от переполнения.
- Frontend Playwright/Chromium: вкладки VPN/TURN выбирают настоящий профиль, запоминают выбор в сеансе, пустой режим не подключает профиль другого типа, локальный флаг Казахстана загружается, нейтральные подписи интерфейса; навигация, connect/disconnect, профиль/поиск, ошибки импорта и очистка поля, настройки, диагностика, компактное окно, reduced motion и вывод недоверенного имени через textContent.
- Официальный CAPTCHA SDK: mock frame с тем же origin/source-протоколом, отклонение поддельного postMessage от другого source, приём результата из ожидаемого mock iframe, одноразовая передача и отмена. Реальные ресурсы поставщика при этом перехвачены и не запрашиваются.

Проверены Vokop v3, наследование routing/turn.options и явные локальные overrides, all+exclusions, bounds настроек, просрочка, будущая дата, rollback revision, дубликаты JSON, четыре официальных домена звонка, безопасные HTTPS-ссылки. Старый формат состояния 0.1.0 сохраняется.

## Проверка в GitHub Actions

Workflow запускается при push в main, pull request или вручную. Он настроен на:

1. Windows unit tests импортёра/DPAPI/сетевой валидации в x64.
2. Те же тесты в x86 под WOW64.
3. Общие native tests.
4. Сборку и упаковку обоих EXE.
5. Запуск настоящих desktop EXE с WebView2 и Playwright через CDP: получение Go Snapshot, импорт синтетического VLESS без подключения, DPAPI-файл без открытого UUID, сохранение настроек и screenshot.

Smoke-сценарий **не стартует VPN и не меняет маршруты/Firewall**. Порт remote debugging задаётся только окружением теста; в обычном запуске приложение его не включает. [Первый запуск CI](https://github.com/remzone/blink_windows/actions/runs/44128014115) завершился **до старта runner**: GitHub сообщил `The job was not started because your account is locked due to a billing issue.` Ни одного Windows test/smoke step в этом запуске не выполнялось, CI artifacts не созданы. Это ограничение аккаунта, не результат компиляции или теста. После устранения billing-блокировки workflow можно запустить вручную; успешного Windows-результата пока нет.

## Как воспроизвести frontend-тест

Нужны Node.js и Playwright; для Windows-сборки они не нужны.

```bash
npm install --prefix work/ui-test --ignore-scripts --no-audit --no-fund playwright@1.58.2
NODE_PATH="$PWD/work/ui-test/node_modules" BLINK_CHROMIUM=/path/to/chrome node tools/test-ui.cjs
```

Если BLINK_CHROMIUM не задан, используется браузер, установленный Playwright. Снимки сохраняются в `work/ui`. Mock backend не подтверждает работу Win32/COM или VPN.

На Windows с собранными EXE и установленным WebView2:

```powershell
$env:NODE_PATH = "$PWD/work/ui-test/node_modules"
node tools/test-windows.cjs amd64
node tools/test-windows.cjs 386
```

## Что остаётся проверить на целевых устройствах

- Физическую Windows 10 x86, а не только 32-битный процесс в WOW64.
- Wintun, адреса, маршруты `/1`, NRPT, Firewall, cleanup/Recover и отсутствие DNS/IPv6-утечек на Windows.
- Реальные IPv4 VLESS/REALITY, WG/AWG, TUIC, Hysteria, XDRIVE; dual-stack WG с явным IPv6 и сервером, который его обслуживает.
- Live TURN и ручную CAPTCHA с действующей подпиской; mock SDK bridge не гарантирует совместимость настоящего задания поставщика.
- Корпоративные политики, параллельные VPN, сторонние антивирусы, сон/пробуждение, смену Wi-Fi/Ethernet, аварию процесса и восстановление.
- Масштабирование 100/150/200%, многомониторность, Narrator и крупные списки на реальной Windows.

EXE не имеет Authenticode-подписи; установщика, постоянного kill switch, службы и автообновления нет. Эти возможности не заявляются как реализованные.

Frontend проверяет подписку из 120 синтетических серверов: автоматический выбор после импорта, чистый поиск, внутреннюю прокрутку, фильтры 120/60/60, поиск страны на английском по русскому имени, выбор последнего сервера клавишей Enter, пустой результат и сброс. Архивы 0.2.x отозваны. Диагностические ZIP preview находятся в `testing/0.3.0-preview.4`, хеши — в `SHA256SUMS`. Они не обозначены как успешно проверенные реальным Windows runner.


## Регрессии preview

- Go race tests: независимые VPN/TURN-источники, их отдельное обновление/revision, сохранение ручных конфигураций, миграция старого single-source состояния, round trip выбора каждого типа, сохранение выбора при обновлении panel ID.
- Go race tests: отмена и deadline при заблокированном fake-драйвере; поздний результат очищается, повторный старт до очистки отвергается. Реальный Wintun этими тестами не проверяется.
- Progress/report: классификация DNS и авторизации без raw-секретов, ограничение кольца, код тайм-аута.
- Windows unit tests скомпилированы: Snapshot с несколькими источниками не раскрывает URL/ключи; запоздалый failure старого туннеля не затрагивает текущий.
- Frontend: несколько карточек источников и независимые refresh ID; стадии запуска, доступная отмена, постоянный START_TIMEOUT, копирование отчёта, поиск и выбор из 120 серверов.

Пользовательский лог preview.2 подтвердил: очистка успешна, ошибка находится на этапе Firewall в Configure (внешний HRESULT 0x80131500). Последующий лог preview.3 показал тот же отказ с Windows 0x80070057 InvalidArgument. Preview.4 использует прямой WFP API вместо создания NetSecurity-правила. 18 ноября пользователь подтвердил работу подключения в preview.4. При новом отказе нужны файлы из «Диагностика → Открыть папку журнала». В этой среде Windows-драйвер, PowerShell/NRPT и подключение к реальному серверу не запускались.

Windows smoke-сценарий также добавляет независимый TURN fixture после обычного VLESS и проверяет обе группы и источники через настоящий Go Snapshot, не подключая VPN. Этапы сети в отчёте различают адаптер, привязки IPv4/IPv6, MTU, адрес, DNS, маршрут, NRPT и Firewall; из stderr допускаются только фиксированный маркер и числовой HRESULT. Windows-тест проверяет, что произвольный stderr не попадает в сообщение.


## Файловая диагностика preview.2

- Go race tests: конкурентные записи JSONL, чтение до закрытия файла, append после перезапуска, ротация/ограничение размера и обнаружение ошибки записи.
- Переносимый тест парсера cleanup: допускаются только известные этапы, числовые коды и технические идентификаторы; произвольный stderr и дополнительные поля отбрасываются.
- Windows-тесты дополнены выполнением настоящего PowerShell со всеми сетевыми cmdlets, заменёнными локальными mock-функциями: пустые правила/адреса/маршруты не вызывают удаления, чужое правило не удаляется, ошибка NRPT не мешает остальным шагам и не раскрывает сырой текст. Тесты только кросс-скомпилированы; фактический Windows-запуск в этой среде недоступен.
- Frontend проверяет путь журнала, кнопку открытия и видимую ошибку записи. Windows smoke дополнен проверкой создания JSONL и отсутствия фиктивных реквизитов/адреса сервера в журнале; запуск этого smoke пока не подтверждён.

Лог не доказывает исправление соединения заранее: он нужен, чтобы установить точный сбой Windows вместо общей ошибки очистки.


## Регрессии Firewall preview.3

- Переносимые race tests проверяют создание IPv6-only фильтра для полных IPv4-профилей VPN/TURN, отсутствие глобального фильтра в частичном и dual-stack профилях, сохранение двух IPv4 /1-маршрутов.
- Парсер допускает технические идентификаторы вроде `Windows System Error 87,New-NetFirewallRule` и сохраняет CIM/внутренний HRESULT, отбрасывая неизвестные шаги, raw-сообщение и TargetObject.
- Тест ConnectionTrace различает Warning/Info/Error Xray и не переводит предупреждение в состояние failed.
- Windows mock-тест проверяет PowerShell binding `RemoteAddress=Any6`, outbound Block, Profile Any и Enabled True; отдельная ветка имитирует отказ с приватным текстом и проверяет структурированный marker. Сетевые cmdlets полностью заменены функциями; реальные маршруты и Firewall тестом не меняются. На Linux выполнена только кросс-компиляция этих Windows-тестов.

Работа самого NetSecurity/Any6 на пользовательском Windows и реального VPN после исправления в этой среде не проверена. Пользовательский лог не сохраняется в репозитории.


## Регрессии WFP preview.4

- `go test -race ./internal/...`: успех установки/commit, отказ Open/Begin/Install/Commit, порядок abort→close, обязательное закрытие даже при ошибке abort и сохранение исходной причины. Это тесты lifecycle с callbacks; API Windows в них не вызывается.
- Полные IPv4-профили VPN/TURN требуют native guard; частичные OS routes и явный dual-stack его не включают. Скрипт настройки не содержит New-NetFirewallRule/RemoteAddress. Старый PowerShell mock-тест заменён сценарием, в котором любой вызов New-NetFirewallRule запрещён, а ошибка DNS проверяет оставшуюся диагностику; Windows-тесты кросс-скомпилированы, не запущены на Linux.
- Обе Windows-компиляции проходят compile-time ABI assertions: filter/session/sublayer/condition/value sizes и offsets weight/action/context/filter ID. Для x86 используется отдельная структура с padding; структура x64 не переиспользуется с неверным layout.
- Проверка escape analysis компилятора подтвердила heap allocation перед syscall для filter, ID, sublayer, appID pointer и session config. `go vet` проходит на amd64/386.
- Backend не меняет Native snapshot (89 файлов). В пользовательский UI добавлен только понятный этап защиты IPv6; в файл — события WFP и числовые коды API. Приложенный пользовательский журнал в репозиторий не копируется.

Подтверждение работы подключения не заменяет отдельные проверки арбитража WFP, исключений транспорта/NDP/DHCPv6, удаления фильтров при аварии и отсутствия IPv6-утечек. CI runner ранее не стартовал из-за billing-блокировки аккаунта; локальная кросс-компиляция не является Windows runtime-тестом.
